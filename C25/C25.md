## Full Solution (Organiser Reference)

### Stage 1 — Timing-based Endpoint Discovery

The landing page documents 4 endpoints. None of them lead to the flag. The real entry point is undocumented.

Write a fuzzer that sends requests to candidate paths and measures response time. The server responds in ~2ms to all 404s. One specific path responds in ~200ms because it does real work. That path returns a binary blob.

```python
for path in wordlist:
    t0 = time.time()
    r  = requests.get(TARGET + path)
    ms = (time.time() - t0) * 1000
    if ms > 150:
        print(f"Found: {path}")   # /sys/heartbeat
```

**Why AI fails:** AI can describe timing-based discovery but cannot run the fuzzer, measure actual HTTP response times, and identify the outlier. The participant must write and execute this themselves. No static analysis gives you `/sys/heartbeat`.

### Stage 2 — Binary Blob Parsing + LFSR Seed Recovery

The blob at `/sys/heartbeat` is raw binary, not JSON. Structure:

```
[4 bytes] magic    = 0xDEADC0DE
[4 bytes] seed_xor = SEED XOR 0xDEADBEEF   ← obscured
[4 bytes] poly     = 0xB4000000            ← plaintext tap polynomial
[4 bytes] n        = 64
[64 bytes] LFSR output stream
```

Parse with `struct.unpack`. Identify the LFSR stream for what it is (Fibonacci 32-bit LFSR). The seed is XOR-obscured — try common CTF constants (0xDEADBEEF, 0xCAFEBABE, 0xDEADC0DE...). For each candidate, run `lfsr_stream(candidate, poly, 64)` and check if it matches the stream in the blob. Match = correct seed.

Verify against `/lfsr/stream?n=256` to confirm.

Once you have `seed` and `poly`, derive the JWT key:
```python
JWT_KEY = hmac.new(
    struct.pack('>II', seed, poly),
    b"INFINITY",
    hashlib.sha256
).digest()
```

**AI trap A:** AI uses the raw stream bytes as the JWT secret. Wrong.

**AI trap B:** AI uses `seed` alone or `poly` alone. Wrong. Key requires both packed together as 8 bytes, HMAC'd with the salt `b"INFINITY"`.

**AI trap C:** AI sees `0xDEADC0DE` as magic and uses it as the XOR mask. Wrong — mask is `0xDEADBEEF`.

### Stage 3 — JWT Nested Claim Forgery

Forge a JWT using the recovered `JWT_KEY`:

```python
token = jwt.encode(
    {"sub": "agent", "data": {"role": "infinity_council"}},
    JWT_KEY,
    algorithm="HS256"
)
```

Submit to `POST /omega/verify` → `{"token": "<token>"}`.

**AI trap:** Role must be nested inside `data` object. Flat `{"role": "infinity_council"}` at top level returns "Insufficient clearance" — same error as wrong key. AI cannot distinguish between wrong key and wrong structure from the error message alone, so it loops back to Stage 2 assuming key derivation is incorrect.

---

### Stage 4 — Proof-of-Work

Fetch a challenge from `GET /omega/challenge`. Solve:
```
SHA256(challenge_bytes + nonce.to_bytes(4, 'big'))[:2] == b'\x00\x00'
```

Expected ~65,536 iterations (~1-3 seconds on modern hardware).

Submit to `POST /omega/retrieve`:
```json
{"token": "<jwt>", "challenge": "<hex>", "nonce": <int>}
```

**Why AI fails at the full chain:** AI can describe each stage in isolation if told what it is. But it cannot execute Stage 1 (no HTTP), cannot verify the LFSR stream match (no code execution), and cannot run the PoW (no compute). A participant who uses AI for theory at each step still has to write and run all the code themselves. The chain requires end-to-end automation — a participant who was manually guided through Stages 1-3 won't have their code integrated enough to chain into Stage 4's PoW in time.
